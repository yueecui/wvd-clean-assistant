# WVD 装备扫描（截图 + masterdata 校验 + 规则评分）

截屏 + OCR 采集装备，用 masterdata 校验名称与阶数，按**自定义规则**打分。
只读屏幕，不注入、不挂钩、不碰网络。

## 采集字段

| 字段 | 来源 |
|---|---|
| 名称 | 详情标题，剥离 `+N` 后用 masterdata（855 个中文名）校验 |
| 阶（rank） | masterdata `Equipment.rank`，实测 1～6（0 为特殊条目） |
| 类型 | masterdata `EquipmentType`（34 种，短剑/单手剑/双手斧…不同武器分开） |
| 强化 | 名称末尾 `+N`（如「水零轻斧+10」→ 名称「水零轻斧」+ 强化 10） |
| 星级 | 详情名称下方白色星星聚类（1～5 星） |
| 附加加护 | 详情 `附加加护` 区**仅已解锁**词条 |
| 锁定 | **只看详情面板**名称下方那个圆形图标：米黄闭锁 = 锁定，灰色开锁 = 未锁定 |

> 锁定判据（`parse.has_lock_icon` + `parse.detail_lock_box`）：
> 窗口固定成「名称左侧 70~15px、名称下方 8~58px」的小方块，只框那一个圆形图标。
> 锁定 = **米黄**挂锁，未锁定 = **中性灰**的「开锁」图标；光精 / 极光系列的图标金光
> 是饱和黄（`b≈60`、`r-b≈170`），挂锁是米黄（`b≈110~126`、`r-b≈40~56`），
> 所以颜色条件限定在窄带 `b>100 且 40<r-b<120`；光晕边缘的过渡像素（实测 ≤35、15x10
> 的横条）靠「最大连通域高≥12、宽≥8、高/宽≥0.7」再排一遍。详情面板的锁被暗色锁孔
> 切成几块（48+46+31），所以尺寸只看最大那块、总量另算。
> **列表行上的挂锁不参与判断**：金色装备的光晕正好糊在图标右上角（光精系列整行
> 500+ 米黄像素），怎么设阈值都不稳。

## 评分规则系统

规则 = `rules/<规则名>.json`（文件名即规则名，目录运行时按需创建）。匹配时
**按特定装备的规则总是先于按装备类型的规则**（与 priority 无关），同一范围内按
**priority 降序**取第一个匹配的（数值大的先）。

```jsonc
{
  "id": "r_weapon_low",
  "name": "武器 · 强化<20",
  "priority": 10,
  "enabled": true,
  "note": "",
  "color": "#60a5fa",            // 规则颜色（#rrggbb，空 = 默认灰）：规则列表 / 结果列表 / hover 里给规则名上色
  "target": {
    "reinforce": "lt20",          // "lt20" 强化<20 | "gte20" 强化≥20（必选二选一）
    "rank": { "op": ">=", "value": 0 },  // 阶级条件：op 取 >= > = < <=，value 为阶级数字，默认 >=0 不限制
    "stars": { "op": ">=", "value": 1 }, // 星级条件：同上，value 取 1~5，默认 >=1 不限制
    "color": { "op": ">=", "value": 1 }, // 品质色：1白 2绿 3蓝 4紫 5红，默认 >=1 不限制
    "mode": "types",              // "types" 按类型 | "equipment" 按指定装备（互斥）
    "types": [101, 103, 200],     // EquipmentType.id，可多选
    "equipment_ids": [],          // Equipment.id，可多选
    "attrs": ["攻击力"],          // 必有属性：全部命中（空数组 = 不限制）
    "attrs_opt": ["会心", "命中"],// 可选属性：至少命中 attr_need 个（空数组 = 不限制）
    "attr_need": 1                // 可选属性至少命中几个（1 ~ min(可选属性数, 4)）
  },
  "base_score": 30,                              // 命中 target 就先加的基础分，默认 0
  "rank_scores": { "4": 20, "5": 50, "6": 80 },  // 阶级分：键为装备阶级（0~6），0 = 不加
  "star_scores": { "4": 10, "5": 30 },           // 星级分：键为装备星级（1~5），0 = 不加
  "attr": { "攻击力": 1.0, "会心": 0.6 },        // 属性 → 权重
  // 组合按顺序判定，取第一条能得分的；tiers 是阶梯分，键为满足个数（2 ~ min(属性数, 4)）
  "combos": [ { "attrs": ["攻击力", "会心", "命中"], "tiers": { "2": 100, "3": 200 } } ]
}
```

```
评分 = 基础分 + 阶级分 + 星级分 + Σ(词条数值 × 该属性权重) + 类型分
```

- **类型分**：从前往后判定，**第一组命中就取它的分，后面的不再计算**（所以顺序可调，
  靠前的更优先）。组内按阶梯给分——装备实际满足 `k` 个属性就取 `tiers[k]`，取可达的最高档
  （档位 1 ~ min(属性数, 4)，满足 5 个也按 4 档算；某一档没填分数会自动往下找更低档）。
  老格式 `{"need": 2, "bonus": 30}` 自动转成 `{"tiers": {"2": 30}}`，行为不变。
- **阶级分 / 星级分**：命中规则后按装备阶级（0~6）/ 星级（1~5）查表加分，表里没有该值就是 0；
  界面上 0 分项保存时自动丢掉（`rank_scores` / `star_scores` 里只留非 0 项）。
- **目标拥有属性**分两段：`target.attrs` 是**必有属性**（必须全部命中）、`target.attrs_opt` 是**可选属性**
  （至少命中 `attr_need` 个，1 ~ min(可选属性数, 4)）；两段都为空则不限。
  属性名精确匹配（`攻击力` 与 `攻击力%` 是两项，与类型分同口径）。
  老规则只有一段 `attrs` + `attr_need`，读入时整体搬到可选属性，语义不变。

- **基础分**：只要装备符合该规则的 `target` 条件就先加上，默认 `0`；即使一条词条都没配上，
  也能让特定装备稳定大于 0 分。老规则文件没有这个字段时按 0 处理。
- 词条数值：`魔力+3`→3；`抵抗+15%`→15（百分比按数值算）
- 未配置权重的属性按 0 计；非数值词条（如套装技能）忽略
- 没有任何规则匹配 → 0 分（也不会有基础分），列表显示「未匹配」

界面「评分规则」页：左侧规则列表（点卡片直接编辑 / 启用开关 / 复制 / 导出 / 删除），
右侧表单（基础分、强化条件、阶级条件、星级条件、范围模式、类型多选、权重表、组合编辑器）。改动即时重算全部结果。
优先级直接改表单里的数字（同范围内数值大的先匹配），文件名与规则名一致。

## 使用

```
python app\main.py     # 源码（开发环境）：http://127.0.0.1:23456/，可先 pnpm dev 起前端(5173) 走代理
wvd-clean.exe          # 绿色版（23333）：dist\WvdClean\ 整个目录拷走
```

### 开发模式（前后端分开，改前端不用重新打包）

```
# 终端 1：后端（源码默认 23456，不自动开浏览器）
$env:WVD_NO_BROWSER=1; python app\main.py

# 终端 2：前端（5173，热更新，/api 自动代理到 23456）
cd web; pnpm dev
```

- 平时只要**改前端**：开着 `pnpm dev`，浏览器用 http://127.0.0.1:5173，保存即生效。
- 后端换了端口：`$env:WVD_BACKEND="http://127.0.0.1:8766"; pnpm dev`；后端也可用 `$env:WVD_SCAN_PORT=...` 覆盖。
- 只有要在后端端口直接访问或打绿色版时，才需要 `cd web; pnpm build`。

1. MuMu 进入带装备列表的界面（如铁匠铺「装备强化」）。
2. **▶ 开始扫描**：自动回列表顶部 → 逐件点击读详情 → 向下滚动 → 到底自动停。
3. 「待确认」页签集中处理识别不准的条目（校准一次，永久生效）。
   列表顶部的**类型下拉**：单手 / 双手武器可以先选大类，也可以展开到具体武器类型
   （短剑 / 刀 / 忍者刀 / 投掷忍具 …，内部值用 `k:<kind>`）；头 / 手 / 胴 / 盾 / 脚 / 饰品
   本身就是具体类型，不再细分。
4. 配好规则后按评分排序挑装备；**导出 CSV**（utf-8-sig）。

实测 458 件全流程通过，1.5～2.5 秒/件（系统负载高时 7～9 秒/件）。

### 截图 / OCR 流水线

点击 + 截图在主线程，识别放在独立的 OCR 线程，两者并行（生产/消费队列，上限可配 1~8，默认 4）：

- 主线程点完一行就立刻截下一行，不再等这一行的识别结果；识别慢时就排队，队列满则等一等。
- OCR 单线程按入队顺序消费，所以落库顺序、`#` 序号与列表顺序一致；多线程识别能更快，
  但会打乱顺序并成倍吃 CPU，暂不做。
- OCR 引擎加了一把锁：滚动后主线程识别列表行时，会和 OCR 线程串行（只等一次识别的时间）。
- 扫到底会先把队列跑完再报完成，件数与落盘内容都不会缺尾巴。
- 日志里的 `(OCR x.xs / 共 y.ys)` 分别是识别耗时和这一件从点击到落库的总耗时。
- 队列上限在界面右上角「队列」里选（1~8，存在 `config/settings.json` 的 `ocr_queue`）：
  太小截图跑不起来（等于回到串行），太大白占内存（一张 PNG 约 1~2MB）。改动对**下一次扫描**生效。

### CPU 占用

`rapidocr_onnxruntime` 不接受 `intra_op_num_threads` 参数，默认会让 ONNX Runtime 按 CPU
核心数开满线程，扫描时把 CPU 占满、抢卡前台。现在改为在创建会话前替换它的
`SessionOptions` 工厂真正限线程，并在任务运行期间把进程优先级降到「低于正常」。
界面右上角可切换档位：

| 档位 | OCR 线程 | 任务优先级 | 说明 |
|---|---|---|---|
| 均衡 `balanced` | 2 | 低于正常 | 默认 |
| 省资源 `quiet` | 1 | 低于正常 | 每件之间额外让出 0.15s，最慢 |

档位存在 `config/settings.json` 的 `cpu_mode`，切换后对下一次 OCR 会话生效（会重建会话）。
旧版的「全速 `fast`」已下线（开满线程会抢前台），旧配置启动时自动迁移成 `balanced`。
另外扫描时改为**增量评分**（只给新条目打分、重算同装备名内排名），不再每件重算全表。

### 界面状态记忆

- **后端配置**（`config/settings.json`，换浏览器/换设备都一样）：CPU 档位 `cpu_mode`、OCR 队列上限 `ocr_queue`。
- **浏览器本地**（`localStorage`，键前缀 `wvd.`）：结果表的过滤器（类型 / 星级 / 颜色 / 阶级 / 命中规则 /
  待匹配 / 锁定 / 手工分组 未分组·1·2·3·√）、装备名搜索词（`wvd.result.query`，输入框右侧 ✕ 一键清空）和
  排序方式（按序号 / 按评分）、规则页的分类分页（全部 / 强化<20 / 强化=20，`wvd.rules.page`）。
  星级 / 颜色 / 阶级三组都是**多选**（`wvd.result.star` / `wvd.result.color` /
  `wvd.result.rank`，逗号拼接），互相独立、同时生效，每组标题右侧可单独「重置」；
  阶级选项按结果里实际出现的阶级生成。
  命中规则过滤存的是 `rule_id`（`wvd.result.rule`），规则被删掉会自动回落到「全部规则」。
  刷新页面、切到规则页再切回来都不会重置。存的是 UI 偏好，隐私模式或写不进去时只是不记得，不影响使用。
- **类型顺序**：单手武器 → 双手武器 → 头 → 手 → 胴（身体）→ 盾 → 脚 → 饰品，
  扫描列表的类型筛选和规则编辑器的类型分组都按它排（`web/src/parts.ts` + `master.PART_ORDER`）。
  没有可获取装备的类型不输出：109「投掷武器」全表只有一条未翻译的开发用条目
  「投擲（ボニー用）」，所以单手武器下只保留 106「投掷忍具」（`master._usable_kinds`）。

## 自动处理

顶部页签分两组：**装备梳理**（扫描 / 评分规则）与 **自动处理**（强化白装 / 改造绿装 / 自动提炼 / 自动出售）。

**统计是累加的**：改完过滤器再次开始并选「继续加载日志」，日志、每批结果、总数
（件数 / 金币 / 稀有石头）和开始时间都接着上次算，批号也往下排（日志里会写
「继续（已完成 N 批，接着累加）」）；中途停止时这一批不计入。要归零就「新建日志」。

**日志落盘**：开始后在 `log/` 下建一份 `<refine|sell>_YYYYmmdd_HHMMSS.json`，
存日志行、每批结果、总数与起止时间，每次写日志都同步落盘（进程重启不丢）。
所以「▶ 开始提炼 / 开始出售」的弹窗里有两个按钮：

- **新建日志**：新开一份文件，统计从 0 开始；
- **继续加载日志**：沿用当前日志文件继续累加，批号 / 总数 / 开始时间都不重置
  （当前日志是空的时按钮禁用）。

工具栏的「打开日志」列出 `log/` 下同类型的所有日志（显示批次数与起止时间，当前那份带
「当前」角标），点一份即加载进面板；刷新页面或重启后端时，面板会自动读回当前日志。

### 自动强化白装（顶部页签 · 强化白装）

把持有一览里所有**白色 4~5 星**装备逐个强化到 **+5**（到 +5 会变绿），跑完即止，不落日志文件。

前置（脚本不会替你切界面）：

1. 游戏进入「铁匠铺」 → **「装备强化」** → 「持有一览」；
2. 配好过滤器，让列表里只出现白色装备（不限星级；想只强化 4~5 星就自己筛）。

点「▶ 开始强化」会弹确认框（带该页签自己的过滤器笔记，可随手记下常用的过滤条件）。

执行循环（`app/enhance.py`）：

| 步骤 | 动作 |
|---|---|
| 1 | 列表筛选：名字是**白色**就点开（+5 一定变绿，所以白色 = 还没到 +5，不限星级） |
| 2 | 详情确认：颜色白、当前 +N < 5（名字不比对，字体糊 OCR 常差一个字） |
| 3 | 有节奏地连点 `5-N+1` 下「强化」（多 1 下容错），再等名字里的 +N 跳到 5 |
| 4 | 跨过 +5 会弹「附加加护解锁」浮层，点「点击后关闭」 |
| 5 | 当前屏没有待强化的了 → 往下滚一屏；滚不动 = 到底 |

从列表**当前所在位置**开始，不回到顶部；所以跑完一轮后想从头再扫，先在游戏里自己拉回顶部。

识别要点：

- **到顶判据**：按钮区红色像素（正常「强化」≈13，红色「前往合一」≈9373）——只认颜色，
  不全靠 OCR，漏一个字就会误点进合一界面；
- **星级**：不做限制（想强化低星白装也行），星级只在日志里显示，方便回看；
- **顶部半截行不点**：列表最上面只露出一截的行（y < 300）坐标落在列表外，点了选中的还是上一件，
  会表现为日志反复刷「已经是绿色，跳过」。这类行直接跳过；同一个名字最多试 2 次，
  连续 4 次没强化成功就往下翻一屏，不可能原地打转；
- **强化值**：读名字后缀 `+N`（`match.split_reinforce`），+0 时名字上没有后缀；
- **点按节奏**：像玩家一样连点（间隔 0.55 秒，比需要的次数多按 1 下做容错），不再点一下确认一下。
  一次点按要几秒才落地，所以连点完再轮询「+N 跳到 5」，安静 2.5 秒没变化就认为这轮处理完，
  没到 5 就补点（最多补 3 轮）。到 +5 弹的浮层会挡住点击、吃掉多出来的那一下，
  红色「前往合一」只在最后一下落地后才出现，那时已经停手，不会误碰。

### 自动提炼（顶部页签 · 自动提炼）

前置（脚本不会替你切界面）：

1. 游戏进入「铁匠铺」 → **「提炼」** → 「持有一览」；
2. 配好过滤器，让列表里只出现要提炼的装备（红色加粗）。

点「▶ 开始提炼」会弹确认框，**必须勾选「我确认已经配置好过滤器」才能开始**（每次都要重新勾）。

执行循环（`app/refine.py`）：

| 步骤 | 动作 |
|---|---|
| 1 | 点底部「全选」→ 弹出「一键提炼」筛选对话框 |
| 2 | 点 OK → 弹出确认对话框（列出本次要提炼的装备） |
| 3 | 点 OK → 提炼动画 → 「提炼结果」面板（成功 X/Y） |
| 4 | 点「关闭」回到列表 → 回到 1 |

**终止条件**：筛选对话框里的 **OK 按钮变暗**（此时面板提示「没有符合条件的物品。」）；
另外全选后不再弹对话框也算结束（连续 2 批）。单批上限由游戏决定（一次最多 100 件）。

界面识别不做 OCR，只看底部按钮区的亮像素（`900x1600` 基准，按实际分辨率换算）：

| 状态 | 判据 |
|---|---|
| 列表页 | 右下「全选」复选框亮（≥250 像素） |
| 对话框 | 左下「取消」亮（≥1000 像素） |
| 提炼结果 | 只有中间「关闭」亮（≥300），两侧全暗 |
| OK 可点 | OK 按钮亮像素 ≥400（变暗时实测 0） |

两种对话框外观差别很大（确认框整片橙色装备卡，橙色像素 6 万+ vs 筛选框 1 万），
所以点完筛选框的 OK 后**等确认框真正出现再点第二次**，不会因对话框过渡而漏点。
「成功 X/Y」这行字又小又淡，直接 OCR 读不到，先二值化再放大 2 倍才稳定。

**稀有改造石统计**（结果表里的「下改」「全改」两列）：提炼有很低的概率额外产出
**下级全改造石** / **全改造石**。它们出现时一定排在提炼结果面板最上面、行底色高亮
（RGB≈(23,96,104)，普通行 (32,46,48)），一次可能好几个，所以每批只扫前 5 行：

- 高亮行 → OCR 该行名字（放大 3 倍直接读，不用二值化）；
- 名字含「全改造」即为稀有石头，再用「首两字有『下』或文字宽度 ≥115」区分
  （实测 `下级全改造石` 宽 136、`全改造石` 宽 96）；
- 遇到既不高亮、名字又带数值的普通行就停；高亮但认不出名字会记 `⚠` 日志，不硬猜。

### 自动出售（顶部页签 · 自动出售）

前置（脚本不会替你切界面）：

1. 游戏进入「道具店」 → **「出售」**；
2. 配好全部出售的过滤器。

点「▶ 开始出售」同样会弹确认框，**必须勾选「我确认已经配置好过滤器」才能开始**（出售不可撤销）。

执行循环（`app/sell.py`）：

| 步骤 | 动作 |
|---|---|
| 1 | 点底部「全部出售」→ 弹出「全部出售」筛选对话框（要先问服务器，弹框比提炼慢） |
| 2 | 点 OK → 弹出确认对话框（整片橙色装备卡 + 金币变化） |
| 3 | 点 OK → 与服务器交互（列表页右下「正在连接…」）→ 结果弹窗「出售持有物品，获得了 X 金币。」 |
| 4 | 点「关闭」回到列表 → 回到 1 |

**终止条件**：筛选对话框里的 **OK 按钮变暗**（没有符合条件的物品）。单批上限由游戏决定
（一次最多出售 **300 种**），装满就自动下一批。

界面识别同提炼，只看固定区域的亮像素，区别是**不能用 OK 当对话框的判据**：

| 状态 | 判据 |
|---|---|
| 列表页 | 「取消」左半区域（x 200~330）只有约 330 像素 —— 那其实是「返回」一个字角 |
| 对话框 | 同一区域 ≥700（对话框的「取消」压在那里）；OK 变暗时仍成立，所以能认出「没有可出售的物品」 |
| 结果弹窗 | 屏幕中部「关闭」亮（≥300），此时底部按钮区被压暗（左半 0） |
| OK 可点 | OK 整块（x 485~735）亮像素 ≥400 |

结果弹窗的金币数直接 OCR「获得了 X 金币。」（区域 x 100~800 / y 680~900），
读不到就记 0、日志里标 ⚠，不影响继续跑。

## 名称校验与校准

- **已匹配**：masterdata 里有 → 显示图标、id、阶、类型。
- **待确认 / 未匹配**：给出 `difflib` 相似候选（≥0.45，前 6），点「校准」选正确装备，
  映射写入 `config/aliases.json`，**之后同样的 OCR 名自动纠正**，并回填已扫条目。
- 例：游戏里是「踉跄凉鞋」，OCR 读成「跟跑凉鞋」——校准一次全程生效。

## 自动扫描原理

- **逐件点击**：按行坐标 `tap` → 等 0.45s → 截屏 → OCR 详情（名称区放大 2× + 加护区拼成
  **一张图单次 OCR**；每次调用有 1～2s 固定开销，拆成多次小图会慢数倍）。
- **滚动定位**：swipe 距离不可控，用**选中行高亮**当视觉锚点：滚前点最后一行，滚后看高亮
  落在第几行 → 反推整屏全局索引。锚点丢失时退回「名称+星+角标」序列匹配。
- **去重**：全局索引去重。**到底判断**：滚动前后列表内容与坐标完全一致。

## 识别要点（踩过的坑）

| 项 | 结论 |
|---|---|
| 星级 | 白色像素按列聚类，米黄锁被 `b > 0.85r` 自然排除 |
| 锁图标 | 米黄挂锁 `r>150,g>125,r-b>40,g-b>25`；有锁 ~90 像素、无锁 0 |
| 单数字 OCR | 不可用（检测器丢弃窄框），角标只能模板匹配 |
| OCR 线程 | 固定 `intra_op_num_threads=4`，默认 20 线程与模拟器抢 CPU 抖动到 9s |
| ADB 截图 | PowerShell `>` 重定向会损坏二进制，必须 subprocess `capture_output` |
| 名称误判 | 靠 masterdata 校验 + 人工校准，不要只调 OCR |
